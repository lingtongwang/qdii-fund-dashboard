## 文档×代码审计：发现的矛盾与优化点（2026-08-10 第二轮）
> 用户要求审查功能设计与已写代码，找矛盾+优化建议。以下为结论，开工前需先和用户定方案。

### ⛔ 接后端前必须拍板
1. **基金标识 id vs code 冲突**：PRD §4.2 `id:number` 自增、前端 `FundRepository.byId(Number(id))`、localStorage 存数字 id；后端全表以 `code`(6位字符串) 为主键、API `/api/fund/:code`。接真实数据后标识必须是 code。决策：前端改用 code 作 key（推荐，稳定）or API 返回稳定数字 id。
2. **分类体系 静态常量 vs 动态计算**：PRD §4.1 + script.js:38 `const categories` 是写死的固定 pills（美→[纳斯达克,标普,其它]、亚太→[中国香港,其他]…）；后端 §4.5 说 tab/pill 由后端算、前端动态聚合、不写死。后端算出的 pills 是 [日本,香港,印度,亚洲(其他)] 这类，与 PRD 常量对不上。前端 `categories` 常量必须被 API 动态聚合替换。
3. **`hot` 一级 Tab 无后端来源**：PRD 有 'hot' tab（全部 + 主题 pills：全球AI半导体、纳指100），后端分类器只产出 us/apac/europe/other 四个地理 tab，**无 `hot`、无"主题"维度**。主题 pills 后端无从产生。决策：'hot' 改为纯前端"全部+排序"透传（丢主题）/ 或给 config 加手动 theme 标签后端透传（保留主题价值）。

### ⚠️ 实现会导致 bug / 数据错
4. **`manager`/`fm` 字段语义颠倒**：PRD §4.2 `manager`=管理公司、`fm`=基金经理；后端 §4.2 审计表 21/22 反过来（`profile.fm`=基金公司、`profile.manager`=经理）。后端 `funds` 表列 `manager`/`fm` 必须明确语义，mapper 输出对齐 PRD，否则管理公司/经理会串。
5. **`holdings` 字段名不一致**：PRD §4.2 + 前端渲染(1136行 `h.n`/`h.r`) 用 `{n,r}`；后端 §4.3 `holdings(code,rank,symbol,name,pct)` 用 symbol/name/pct。mapper 必须显式把 symbol/name/pct → n/r，文档 §4.4 没给此映射。
6. **前端假定 `ratings` 永远存在**：1214/1215 行 `currentFund.ratings.wind/.star`、1084/1085 对比页 `f.ratings.wind/.star` 直接取，无守卫。后端规则"三级均无值则删除整个 ratings 字段"→ 真实数据下取不到的基金会让前端 `undefined` 崩溃。必须加空值守卫（无评级则隐藏模块）。
7. **`market`/`industry` 空数组无兜底**：后端允许被动基金为空数组，但前端 `renderChart(labels,...)` 空时画空图、穿透聚合 `f.market.data[i]` 空时只累加 0；"不适用"文案后端要求前端显示，代码里没有。需补空态。
8. **`limit` 无限额哨兵 vs 真实值**：前端 102 行 `limit>10000000` 判无限额；后端 `limit_amount` 真实无限额基金可能返回 null/超大数/不返回。null 时 `null>10000000`=false → 显示"null元"。需约定哨兵（建议 null 表无限额）并改 `formatLimit` 处理 null。
9. **`limit` 混淆"申购状态"与"限购金额"**：PRD `limit` 是数值元；后端 §4.2 行3 把 `limit` 来源写成 Wind "运作状态"(文本) 和 lsjz.SGZT(状态)。状态是枚举不是金额。后端 daily_nav 实际有 `purchase_status`+`limit_amount` 两列，但 PRD 模型只有 `limit`。建议 PRD 增 `purchaseStatus` 字段与金额分开，Bottom Sheet 同时展示状态+金额。
10. **缺"数据日期"字段**：后端强调 QDII 净值 T+1/T+2 延迟、UI 要标数据日期（§6注/§8-4），但 PRD Fund 模型无 `dataAsOf`/`navDate`。列表"日涨跌"会误以为是今日。需补字段并在 UI 标注。

## 第三轮（23:26）：上线部署 + Wind 可用性决策（重要架构结论）
- **用户核心疑问**：测试完成后上线到服务器，数据抓取怎么办？还能用 Wind 吗？
- **核实结论**：
  1. Wind MCP Skill 是 **agent 侧工具**，依赖 WorkBuddy agent 运行时 + 本机已授权的 Wind 金融终端；**不是可被独立后端进程调用的服务端 API**。Wind 真正的 Server API (WDS) 是机构付费、需签合同，不向个人开放。→ 生产服务器**不能/不应依赖 Wind**。
  2. 后端文档里"Wind 独占"的字段其实天天基金也能给：天天基金 `f10/tsdata_{code}.html`「特色数据」提供 **标准差(波动率)/夏普比率/最大回撤**；晨星评级在基金页可拿。→ 风险指标不必依赖 Wind。
  3. 既有 T1→T2→T3 兜底设计天然兼容：服务器上**关掉 T1(Wind)**，只用 T2(天天 HTTP)+T3(季报 PDF) 即可，所有字段都能覆盖。
- **推荐生产架构**：
  - 数据来源 = 天天基金 HTTP (T2) + 季报 PDF (T3)，纯出站 HTTP，任何 Linux VPS 都能跑。
  - `adapters/wind.js` 改为**可选本地增强**，用 `USE_WIND` 环境变量在服务器置 false；本地有 Wind 才启用。
  - 风险指标优先从已抓取的 NAV 历史(lsjz)本地计算（年化波动率/最大回撤/夏普），更稳、不依赖解析 tsdata 页。
  - 部署形态：Node 长驻进程(Express + node-cron)，每日 18:30 净值 + 季报首月全量；低频小流量，天天不会限流；需带 UA/Referer 与 ggmx 的 `ut` 令牌；SQLite 落库；前端由 Express 同进程静态托管。
  - 地域注意：服务器尽量选国内/中国香港区域，天天接口海外可能慢或被墙。
- **待办**：后端文档 §2.1/§4.2 应把 Wind 明确降级为「可选本地增强」，生产默认 Eastmoney-only；此决策已与用户对齐（用户认可"不用 Wind 上线"的方向）。
